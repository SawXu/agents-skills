# AI review 讨论处理流程

在用户要求处理已有 MR/PR 的 AI review 时执行。这里的“解决主题”指平台讨论的 Resolve 操作，不是只回复或标记文件已修改。

## 1. 建立讨论清单

确认仓库、MR/PR 编号、源/目标分支及当前分支与远端的对应关系；无法唯一确定时请用户提供链接。用已配置的 GitLab/GitHub CLI 或 API 读取完整讨论（含分页、已解决和过时线程），而非只看 MR/PR 顶层评论或通知摘要。GitLab 核查 discussions 的 `notes`、`resolved`、`resolvable`；GitHub 核查 review threads 的 `comments`、`isResolved`、`isOutdated`、`isResolvable`（以实际接口字段为准）。通过 CLI `--help` 确认当前环境支持的查询和回复命令，必要时使用平台 API；不要猜测命令参数。

识别 AI review 的发言者（机器人账户、已知 AI reviewer 身份或用户明确指定的讨论）；身份不明时先核实，不把人工评论当作 AI 评论。逐条记录讨论 ID/链接、所有评论内容、位置、作者、解决状态和所指 commit；注意同一讨论可能有人工后续回复。默认处理未解决的 AI 讨论；已解决的只用于核对和防止重复回复。完成标准：每条目标讨论的 ID、状态、评论上下文与所指版本均已记录；读取不全时报告缺口，不宣称“全部处理完毕”。

## 2. 逐条判断与处理

结合评论原文、所指版本的 diff 和当前代码及调用方/测试核对问题；过时线程也要判断问题是否已在当前版本修复。不能仅凭“AI 说的”或“diff 已过时”判定对错。每条讨论选择以下路径：

- **问题成立**：做最小范围修复，按项目约定运行相关验证，记录证据（测试结果、代码位置）；失败或无法验证则保留讨论为未解决并说明阻碍。需要改动源分支时遵循现有提交/推送限制；未获推送授权时可以准备本地修复，但不得声称远端 MR/PR 已修好或解决主题。修复已出现在 MR/PR 可见版本且复核通过后，在**原讨论线程**回复修复位置、提交和验证结果，再解决主题。
- **问题不成立或已修复**：在**原讨论线程**给出具体原因和可核对证据（代码路径/行、行为、测试或已有提交），说明为何无需再改；回复成功后，若讨论可解决则解决主题。
- **证据不足、评论有歧义或超出本次授权**：在原线程提出具体待确认点（适当时），保留未解决，不臆断，也不以空泛答复关闭讨论。

如果一个主题包含多个独立问题或人工后续提出的未完成问题，逐项核对；只有全部得到处理时才解决。回复前重新读取讨论状态，避免重复发布；回复后确认回复出现在正确的讨论中，再调用平台的 resolve-discussion/review-thread 操作，并重新读取状态确认已解决。若平台仅提供普通评论或线程不可解决，只回复并报告“无法解决主题”，不可把普通评论、reaction 或整单 approve 当作解决主题。对远端评论和解决动作按用户的处理请求执行；不要擅自推送、重写共享历史或合并 MR/PR。完成标准：每条目标讨论都已作出判断并有证据，回复出现在原线程，所有可解决且已处理的主题经重新读取确认为 resolved；其余逐条记录阻碍。

## 3. 结果回报

逐条列出讨论链接/ID、判断（已修复/不成立/待确认）、修复提交或证据、验证、回复状态与解决状态；区分本地修复与远端可见修复。列出未处理/未解决项及原因；只有全部目标讨论完成回复、且所有可解决的主题均已确认解决，才报告“AI review 讨论处理完成”。
